# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

Terminal-inspired colour schemes for GNOME (GTK 3, GTK 4/libadwaita, GNOME Shell) plus an installer for the themes and for icon sets. A theme is a top-level directory (`gruvbox-material`, `nordic`, `dracula`, `catppuccin`, ...). Each theme takes the *stock* stylesheet unchanged and replaces **colour values only**; selectors, geometry and assets stay stock. The only deliberate additions are two marked override blocks at the end of every generated Shell stylesheet (calendar flat, calendar tiles). `README.md` is the user-facing documentation; `AGENTS.md` is a notice aimed at outside agents.

## Commands

Public recipes (ten, all thin calls into `tools/themectl.sh`; run from the repo root): `list-themes`, `install-theme [scheme]`, `update-theme`, `remove-theme [scheme]`, `switch-theme [scheme] [accent]`, and the same five for icons (`*-icons`, `switch-icon`). Without a name, install/remove/switch show a checklist (SPACE ticks, ENTER confirms, q cancels). `THEMES_DEST`, `ICONS_DEST`, `ICON_SOURCES`, `ICONS_URL`, `CANDY_FOR_GNOME_CACHE` and `FORCE=1` redirect or override the installer, which is how tests stay out of the real home.

Development (private recipes; need python3-gobject, GTK 3, GTK 4 and gnome-shell installed):
- `just generate [scheme|all]` regenerates everything for a scheme (GTK3/GTK4/Shell themes, libadwaita file, accent maps). Generated files are committed; never hand-edit them.
- `just test <scheme>` or `python3 -I tools/selftest.py <scheme> [contrast|gtk3|gtk4|shell|all]` runs the checks for one scheme.
- `just new-scheme <scheme-dir> <ptyxis-palette> [light-palette]` starts a new scheme: `tools/scheme-from-ptyxis.py` writes a DRAFT `scheme.toml` from a Ptyxis built-in palette (`tools/ptyxis-palette.sh list|show <id>`, ids are case-sensitive and UTF-8 (e.g. Rosé Pine), `PTYXIS_BIN` overrides the binary) and prints the TODO decisions (`ptyxis` is already the id; `python3 -I tools/ptyxis-compare.py <scheme-dir>` shows the distance to the candidates); then the normal pipeline. Private recipes still run by name (`just --justfile <file> new-scheme ...`, which is how the image's `ujust candy-for-gnome new-scheme` reaches them). The walk-through is the project skill `.claude/skills/build-scheme/SKILL.md`.
- `tools/test.sh [--rebuild] [--all] [--featured] [--sample N] [scheme ...]` is the whole suite, an OPTIONAL developer tool: **CI on the pull request is the test**, and the local full run is not used (not by agents either; run only quick checks that fit a change: `tools/selftest.py` for the scheme, `tools/ptyxis-compare.py --check`, `bash -n`, shellcheck). It covers (lint, hygiene, regeneration, selftest per scheme, install/switch/update/remove for every scheme and accent, icon recipes). It builds a cached Fedora 45 image from `tools/test.Containerfile` + `tools/test-packages.txt` and runs itself in a throwaway podman/docker container with the repo mounted read-only. It tests the **committed HEAD** (a fresh clone), so commit before running it. The first full run of a change is therefore the CI run on its pull request.

## Principle: the Ptyxis built-in (by id) is the source of truth

For every scheme variant that has a Ptyxis built-in palette, the built-in decides the colours: `bg_deep` and `fg` are its Background and Foreground, the six `[<variant>.ansi]` accents its Color1-6, and its real black, white and brights (Color0, 7, 8-15) sit in `[<variant>.terminal]`; the terminal then shows exactly what the toolkit themes use. Roles that equalled an accent follow it; derived ladder roles (bg, surface, surface_high, fg_dim, comment) keep the fixed rules and are dropped from the explicit table where a changed background or foreground would make the ordering collide. Each variant says `source = "<built-in id>"` (the id it declares: `ptyxis`, or `ptyxis_light` for a flat light built-in) or `no_builtin = "<why>"` (Gruvbox Material light, Material light: the own values stay and the dark built-in serves both modes). There is no "official source" override and no `builtin_differs` any more, and no generated palette. A colour may differ from the built-in only as a **nudge**, forced by a contrast check of the GTK colours (`tools/selftest.py`: fg on window and view at 4.5:1) and listed in `[<variant>.nudge]` as `Key = { from = "<built-in value>", to, de, why }` with at most NUDGE_MAX delta E (one constant in `tools/ptyxis-compare.py`); today Solarized dark and light and Tokyo Night Day carry an `fg` nudge. The terminal itself always shows the built-in unchanged. `ptyxis-compare.py --check` fails on a missing id, a source that is not the declared id, an unlisted difference from the built-in, or a stale or oversized nudge. Nordic (dark only) uses the sectioned `nord` built-in on purpose (`ptyxis_light_section_accepted = true`): under a light system colour scheme Ptyxis shows Nord's [Light] section while the rest of Nordic stays dark. Provenance and credit notes in the `scheme.toml` headers and `NOTICE` say that the colours are taken from Ptyxis's palette of that name (mostly Gogh ports, per each built-in's header) and credit the project that inspired the theme.

## Architecture

**Generation pipeline** (needs several files to see): `<scheme>/scheme.toml` (roles per variant, the six terminal ANSI accents, optional seventh `orange`, `default_accent`) -> `tools/palette-from-scheme.py` derives `<scheme>/palette.toml` (ramps, colour families, exact overrides; the fixed derivation rules are documented in its header) -> `tools/gtk3-theme-gen.py`, `gtk4-theme-gen.py` and `shell-theme-gen.py` read the **stock** CSS from the installed libraries (GTK3 Adwaita and GTK4 Default resources, `gnome-shell-theme.gresource`) and replace colour tokens through the shared engine `tools/themegen.py` -> `<scheme>/themes/<Name>/...`; `tools/libadwaita-gen.py` writes `<scheme>/libadwaita/gtk.css`; `tools/ptyxis-compare.py` checks the Ptyxis declarations (`ptyxis = "<id>"`, optional `ptyxis_light = "<id>"`: Ptyxis BUILT-IN palette ids, nothing is generated for the terminal; see the Ptyxis bullet below; optional `[<variant>.terminal]` tables hold real blacks/brights with their source; shared helpers in `tools/schemeroles.py`); `tools/gtksourceview-gen.py` writes the GtkSourceView 5 style schemes `<scheme>/gtksourceview/candy-for-gnome-<scheme>-{dark,light}.xml` (contrast rule and role mapping in its header). The stock files are recoloured in place because `@define-color` overrides do nothing visible in GTK 3.24 (colours are inlined) and St has no such feature.

**Structure guarantee**: `tools/selftest.py` masks colour tokens in the stock file and the generated file and requires 0 differing lines (the two override blocks, calendar flat and calendar tiles, are stripped first and each checked separately). Stock drift in a newer Fedora therefore fails the regeneration check: run `just generate <scheme>` and commit.

**Accents**: `tools/accent-maps-gen.py` re-runs the recolour per accent, diffs token by token and writes `<scheme>/accents/<accent>.{dark,light}.sed` plus `accents/list`. The maps are two-phase sed scripts (token -> placeholder -> new token) and are verified against the directly generated files. Some `accent_fg` / orange role values are nudged by a few units so every sed key token stays unique (the generated `palette.toml` header says which). Dark-only schemes fill the GTK light slot from the dark palette and have no Shell-Light folder.

**Installer** (`tools/themectl.sh`, one script, `themes` and `icons` kinds): themes copy from the checkout (`update-theme` does `git fetch` + `pull --ff-only` first); icon sets come from the sources in `tools/icon-sources.conf` (`top`, `root`, `script` and `script-t` layouts; Tela and Fluent run their upstream `install.sh` into a temp dir with the variant as a bare argument, WhiteSur uses `script-t`: `-n WhiteSur -t <variant>`, standard = `-t default`, never `-t all`, no `-a/-b/-p`; the registry key is `WhiteSur` because the set base name is the key capitalized; its `-dark`/`-light` folders symlink to the base folder, so the three always install and remove together). The registry DECLARES every set name (column 4: `top` = directories, `dir=SetName` when the installed name differs; `root` = the name; `script` = variants), so listing, the install checklist, switch and remove need no clone and no network; a source is cloned (shallow, under `~/.cache/candy-for-gnome/icons/<source>`) only after the choice, for the sources of the chosen sets (update: of the installed sets), and a failed clone skips just that source. After a clone `verify_source` warns once per mismatch (`registry says X, upstream has no X` / `upstream has Y not in the registry`) and carries on; when an upstream renames or adds a set, fix the registry. Each set's own folder is replaced wholesale, never the whole destination. Installed folders carry a `.candy-for-gnome` marker; a same-named folder without it (for example a third-party `Dracula`) is only replaced after a `y` at the prompt (or `FORCE=1`). Ptyxis palettes are never installed (built-ins only); install, update, switch and remove delete leftover generated palette files of earlier versions from `PTYXIS_PALETTES`, only files that carry the marker line `# candy-for-gnome: <scheme>`, one output line per file (an unmarked file such as a hand-made palette is never touched). `switch-theme` writes the palette ID to the dconf `palette` key of the default profile and of profiles that already have one (`ptyxis` or, for a scheme with `ptyxis_light` under a light system colour scheme, `ptyxis_light`; `pty_mode`: `prefer-dark` dark, `prefer-light` light, `default` dark only when the GTK theme in use is a dark one, no gsettings dark), reads the key back (`Ptyxis palette key reads 'x'`) and warns when the id is not a built-in of the installed Ptyxis (`tools/ptyxis-ids.py ids`). GtkSource style schemes are installed like the palette (marker comment, same guard) into the user styles dir and the data dirs of installed Flatpak editors (they ignore host `~/.local/share`); `switch-theme` sets Text Editor's and Builder's style scheme key where each app reads it (see the GtkSourceView bullet). Flatpak access is managed here too (`fp_*` in `tools/themectl.sh`): after `switch-theme` it offers (prompt, default no; no terminal: prints the command) the missing global read-only entries of one list, records only what it added in `$XDG_STATE_HOME/candy-for-gnome/flatpak-overrides`, and after the last theme and icon set (marker files) is removed it offers to undo exactly the recorded entries; never silent, no new recipe. `switch-theme` applies the accent (sed maps over the installed copies, remembered in `$XDG_STATE_HOME/candy-for-gnome/accents`), sets the GTK and Shell themes (dconf fallback when gsettings lacks the User Themes schema) and the libadwaita file `~/.config/gtk-4.0/gtk.css` (replaced silently only if generated by candy-for-gnome or a `.bak` exists, otherwise it asks).

## Workflow

**Branching (GitLab Flow)**: work happens on feature branches (`feat/<topic>`, `fix/<topic>`, `hotfix/<topic>`) pushed with full refs (`refs/heads/...`). Dev lane: a push to such a branch runs `test` (featured schemes only per scheme, see "CI time and coverage") and `secrets`; the agent opens a PR into `testing` and squash-merges it itself once both are green and no run on `testing` is in progress (a newer merge cancels an older pending run). Testing lane: the merge (a push to `testing`) runs the same featured-scope suite (no longer every scheme). The agent then opens or amends the single promotion PR `testing` -> `main` right away (what it carries, what is verified; no build-state text). Kevin alone approves and merges that PR (merge commit, never squash or rebase). Nothing is published (no image, no release): themes are installed from a checkout, so `main` is just the reviewed result and no back-merge into `testing` is needed. Rulesets and repo settings are applied by the hub, never by the agent.

CI (`.github/workflows/ci.yml`) triggers on push to every branch except `main`, on `pull_request` into `testing`, and on manual `workflow_dispatch` (input `full`, default true). Every run sets `TEST_SCOPE=featured` (feature branches, PRs into `testing`, pushes to `testing`): per-scheme checks cover the featured schemes only (below). Only a manual `workflow_dispatch` with `full: true` (the default) sets `TEST_ALL=1` and checks every scheme; there is no automatic full run. Concurrency groups are per ref and event, so runs of different events do not cancel each other. Jobs: `test` (`tools/test.sh` in a Fedora 45 container) and `secrets` (gitleaks, a pinned release whose SHA-256 is checked with `sha256sum -c` before it runs; `GITLEAKS_VERSION` and `GITLEAKS_SHA256` are env at the top of the job, so a bump changes those two lines, both taken from the release's `gitleaks_<version>_checksums.txt`; full-history scan with `--redact`; no local hooks or `.gitleaks.toml` here); their names are the required checks on `testing` and `main`, so they must not be renamed. `.github/workflows/require-testing-branch.yml` (job `require-testing-branch`, also required on `main`) fails a PR into `main` whose head is not `testing` of this repository. `workflow_dispatch` and this workflow on a PR into `main` only use the copy on `main`, so their first real run follows the first promotion. Both CI jobs use the pinned runner `ubuntu-24.04` (a fixed image so a moving `-latest` cannot change results under us; the test job runs in `fedora:45` anyway) and checkout is pinned by commit SHA. The dnf install of the test packages takes about 90 s per run; a cached test image was not worth a registry push step. CI shellcheck runs at warning level. `update-theme` in the installer pulls the checkout's current branch with `git pull --ff-only` (no branch name hard-coded), so users on `main` get the reviewed result.

Not verified live without Blur My Shell (the overlay then sits on the opaque stock popup surface). The tile overlay lowers the contrast of the tile text a little (35 of 208 Shell variants end up under 4.5:1 in the worst state, 16 already were with the stock tile background; worst Ollie dark 2.85 and Solarized dark 2.87): `selftest.py shell` prints it per theme (`tiles: ... worst blended contrast`) but does not fail on it, like the other secondary contrast lines. Selftest asserts exactly one tiles block at the end, only the three tile selectors, only background/border/radius/shadow declarations and only white or black alpha rgba colours.
- **Accents**: one of the six terminal colours plus orange where the scheme has one (`<scheme>/accents/list`; not `rose-pine` and `fairy-floss`, whose upstream has no orange). Sed maps live in `accents/<accent>.{dark,light}.sed`; the chosen accent is remembered in `~/.local/state/candy-for-gnome/accents`. - **Ptyxis**: every scheme uses a Ptyxis BUILT-IN palette, declared by ID. **Ptyxis keys the profile `palette` setting by palette id, not by display Name** (the resource file name without `.palette`, case-sensitive: `nord`, `dracula`, `solarized` are lower case, `Gruvbox Material`, `Rosé Pine`, `Catppuccin Mocha` are not; both `solarized` and `Solarized` exist and differ); an unknown value makes Ptyxis silently fall back to its default palette (the original bug: the tools listed and wrote Names). `tools/ptyxis-ids.py list|ids|show <id>` (wrapper `tools/ptyxis-palette.sh`) reads the ids from the binary (ELF section `.gresource.ptyxis` -> Gio.Resource); `PTYXIS_BIN` may be a directory of `<id>.palette` files (test fixtures). Declare `ptyxis = "<id>"`; a scheme whose dark and light built-ins are two flat palettes also gets `ptyxis_light = "<id>"` (Catppuccin Mocha/Latte, Tokyo Night/Tokyo Night Day, Rosé Pine/Rosé Pine Dawn); a sectioned built-in (nord, dracula, solarized, Everforest) covers both modes with `ptyxis` alone; where only the dark built-in exists (Gruvbox Material, Material) it serves both modes and `ptyxis_reason` says so. A light/dark pair cannot follow the system by itself (one palette key per profile), so `switch-theme` picks the id by the system colour scheme at switch time and says to run it again after changing light/dark. `ptyxis-compare.py --check` fails on a declared id that is not in the binary (and suggests the right-case id) and reports each scheme's delta E to its built-in as information. There are no generated palettes (a past experiment; `<scheme>/ptyxis/` is gone).
- **GtkSourceView**: installed into `~/.local/share/gtksourceview-5/styles` and, because Flatpak editors only read their own data dir, into `~/.var/app/org.gnome.TextEditor|org.gnome.Builder/data/gtksourceview-5/styles` when installed (no sandbox permission needed). `switch-theme` sets Text Editor's `style-scheme` (-dark while the desktop is dark, else -light) and Builder's only if present. **Flatpak editors keep their own settings store**: the sandbox has no dconf socket and the apps no dconf permission, so a host `dconf write /org/gnome/TextEditor/style-scheme` never reaches them (it reads `~/.var/app/<id>/config/glib-2.0/settings/keyfile`). For an editor that `flatpak info` reports installed, `gsv_set_flatpak` runs `flatpak run --command=gsettings <id> set <schema> <key> <scheme id>` and reads it back the same way; it prints `Text Editor (Flatpak) style scheme is now X` only when the read-back matches, else `WARNING: ... reads 'Y'`. Keys: `org.gnome.TextEditor style-scheme` (Text Editor) and `org.gnome.builder.editor style-scheme-name` (Builder). The host dconf is written only for an editor that is not a Flatpak or when the host also has the schema (`gsettings list-schemas`). The id follows the system colour scheme at switch time; Text Editor's `style-variant` is `follow` and the generated XML carries `variant` plus `light-variant`/`dark-variant`, which is how GtkSourceView-based apps switch to the sibling when the desktop mode changes (taken from that metadata contract; not verified in Text Editor's source or live). Tests use a stand-in `flatpak run` (`FLATPAK_GS`).
- **gsettings backend trap**: the Ghostty AppImage starts shells with `GSETTINGS_BACKEND=keyfile` (its GTK has no dconf module). Then every `gsettings set` lands in `~/.config/glib-2.0/settings/keyfile`, which GNOME never reads, and `gsettings get color-scheme` answers `default` from that private store (the script then picks light themes). `themectl.sh` therefore unsets the variable at startup when it is exactly `keyfile` (one note; other values and an unset variable are left alone, so no forced `dconf` on systems without the module). Any new tool that calls gsettings must go through `themectl.sh` or do the same; the read-only developer tools here do not call gsettings. Syntax colours are held at 4.5:1 on the editor background (comments 3:1) by changing lightness only; the generated file lists what moved.

- **Built-in picker and its viewport rule**: one place for install/remove (`choose_many`) and switch (`choose_one`), themes and icons (the accent submenu uses it too). The frame is 1 header line + H list lines + 1 footer line, H = terminal rows - 2 (at least 1, at most the number of entries); `top` is the first shown row of the (filtered) list and only moves by the minimum needed to keep the cursor row visible (one cursor step moves the window by at most one row; wrapping from the first to the last entry jumps); the footer shows `first-last of total`, the filter and the tick count; lines are cut to the terminal width, the frame is redrawn in place (cursor up H+1, clear to end of line) and the cursor rests on the footer row, so a full-height frame never scrolls the terminal; a size change (polled every 0.3 s in `_tui_wait_key`, `read` is not interrupted by SIGWINCH) clears the screen and redraws from the top. Root cause of the old bug: the picker printed ALL entries and moved the cursor up n+1 lines, which cannot go beyond the screen top when the list is taller than the terminal, so every redraw scrolled the terminal and the view stuck at the bottom. Keys: up/down j/k, PgUp/PgDn, Home/End or g/G, SPACE, a/n (shown entries), `/` filter (substring, case-insensitive; Enter keeps it, Esc clears it; ticks survive), ENTER, q. `tools/pty-scroll-test.py` runs the picker in a pty with a small terminal emulator (10 and 24 rows, 187 entries) and asserts after every key: one highlighted row with the expected entry, header and footer on screen, window top moved by at most one; plus last/first, pages, a filter, off-screen ticks and resizes. ## Scope and delegation

- This repo is its own Claude project: work only inside it. Never edit anything outside it (other repos, the real themes or icons directories, home-directory configs, live gsettings/dconf). Tests use temp dirs and `THEMES_DEST` / `ICONS_DEST`, as `tools/test.sh` does when it is used.
- Anything that needs the outside (applying a theme on the desktop, a live check in the running Shell, a change in another repo) is not done here. Report it as a request under `Needs from hub:` to whoever spawned the session, who handles or delegates it.
- Work on this repo from other sessions goes through a project agent spawned by that hub, not through direct edits to these files.

Licences: tooling and docs MIT (`LICENSE`); each `*/themes/<Name>/` folder carries its own LGPL `LICENSE` because the generated CSS derives from GTK / GNOME Shell stock stylesheets. A new scheme needs its palette credit in `NOTICE`, provenance notes in `scheme.toml`, and the folder `LICENSE` (`just generate` copies it).

## Name history
- The project was called `gnome-themes` until 2026-11-14 (renamed because the GNOME trademark guidelines do not allow a product name that leads with GNOME). Nothing is migrated: the installer does not treat the old marker `.gnome-themes` as its own (not even through the index.theme adoption rule), and when `$THEMES_DEST` or `$ICONS_DEST` holds folders with it, every run prints one message listing them with the `rm -rf` command (never deletes). Environment prefix is `CANDY_FOR_GNOME_` (`CANDY_FOR_GNOME_CACHE`, `CANDY_FOR_GNOME_SKIP_ASSETS`). Keep GNOME descriptive only ("for GNOME Shell"), no GNOME logo or artwork, and the independence notice near the top of the README.
